BinaryStamp

Proof that a file existed,
and that it was yours.

A multi-chain provenance registry. Hash any file in your browser, register that hash on an immutable ledger, and hold a timestamped, independently verifiable record of authorship — without ever revealing the file.

What it is

A registry of hashes, not of files

Drop a file in. It is hashed with SHA-256 entirely in your browser — the bytes never leave your machine. The 32-byte digest is written to a blockchain, signed by your own wallet, alongside an optional description and metadata blob.

Nothing is uploaded

Only a digest is published. The registry never sees your content.

Timestamped by consensus

The block's time is agreed by a network, not asserted by a file header.

Owned by you

Your wallet signs the transaction, so the record is yours and transferable.

The problem

“I had this first” is remarkably hard to prove

Every everyday marker of when a thing existed is either editable, private, or someone else's to withdraw.

What we usually rely on

  • File modification dates — trivially rewritten
  • Email to yourself — provable only if the provider cooperates, forever
  • Cloud storage history — the vendor controls, and can lose, the evidence
  • Notaries and registries — slow, costly, jurisdiction-bound
  • “Posted publicly on this date” — requires disclosing the work itself

What a claim actually needs

  • A time that no single party can move
  • A record that survives the company that made it
  • Verifiable by an opponent, not just by you
  • No obligation to reveal the content to establish the date
  • Cheap enough to do routinely, not only when it matters

The awkward case is the common one: you want to establish that you held an idea on a given date without publishing it — before a pitch, a filing, or a negotiation.

How it solves it

Publish a commitment, not the content

A cryptographic hash is a one-way fingerprint. It is infeasible to derive the file from it, and infeasible to find a different file that produces it. So the digest can be made public while the file stays private.

Hash locally

SHA-256 runs in the browser. A one-byte change gives a completely different digest.

Stamp on-chain

Your wallet signs a transaction recording the digest, the time, and your address.

Keep the file

Nothing is disclosed. The chain holds a commitment to something only you can produce.

Reveal when it matters

Show the file. Anyone re-hashes it, matches the digest, and reads the block's timestamp.

This is the classic commit–reveal pattern. The commitment is public and dated from day one; disclosure happens on your schedule, or never.

Why a blockchain

The value is in what nobody can do

A database with a timestamp column proves nothing to an adversary — whoever runs it could have written that row this morning. The properties that make a claim hold up are all negative ones.

Nobody can backdate
The time comes from block ordering agreed across a network, not from a field someone set.
Nobody can delete
Not the operator, not you, not a court order to a single company.
Nobody can gatekeep
Verification needs a public node, not our permission or our continued existence.
Nobody has to be trusted
The counterparty checks the chain themselves. No shared faith in a vendor.
Nobody learns the content
A digest is public; the file behind it is not.

Worth stating plainly: a stamp proves a digest existed at a time and which key signed it. It does not prove the signer authored the work, nor that the claim is original. It establishes priority and integrity — which is usually the disputed part.

Use case

Intellectual property and priority

Most disputes turn on sequence: who had it first, and has the artefact changed since. A stamp answers both, for a few cents, at the moment of creation rather than the moment of conflict.

Design and creative work

Stamp each iteration. The chain records the whole development trail, dated, before anything ships.

Research and invention

Establish a conception date while a patent is still being drafted, without publishing and destroying novelty.

Trade secrets

Prove a document predates a departing employee's new venture — while it stays a secret.

Contracts and evidence

Show a document is byte-identical to the one agreed on a date. Tampering changes the digest.

Defensive publication

Stamp now, reveal later as prior art to block someone else's downstream claim.

Journalism and sources

Fix a chain of custody for material whose date is later challenged.

Use case — where this goes next

Agents proving, and reusing, work

Computation is deterministic: the same data through the same function yields the same result. That makes the inputs addressable — and a registry of input digests becomes a shared, verifiable memo of work already done.

key = sha256( data ‖ function ) what was asked stamp = key on-chain, signed, timestamped metadata= sha256( result ) + Walrus blob what came back agent A computes, stamps key, attaches result agent B derives the same key → already stamped → fetches result ── skips the work, verifies by re-hashing what it fetched

Don't repeat expensive work

An identical job across organisations resolves to the same key. Fetch instead of recompute.

Attribution for agents

The signature says which agent produced a result, and when. A basis for credit, billing, or audit.

An auditable trail

Reconstruct what an agent was given and what it returned, long after the run.

Honest limit: a stamp proves an agent claimed a result, not that the result is correct. Trust comes from the signer's reputation, from spot-checking by re-running, or — see the next slide — from attaching a proof rather than an assertion.

Under the hood — ENS

Turning a digest into a name anyone can resolve

Every stamp is reachable as a real ENS name in any wallet or explorer — with no subdomain ever registered on-chain. There are millions of possible stamps; minting a name for each would be absurd.

wallet asks for <hash>.binarystamp.eth │ ├─ no such subdomain in the registry ├─ walks up to binarystamp.eth, finds our resolver ├─ resolver supports wildcards (ENSIP-10), so it is asked anyway ├─ it answers with a revert: “not here — go ask this URL” (EIP-3668) ├─ wallet calls our gateway, which queries the subgraph └─ resolver's callback returns the answer → owner address

A deliberate revert used as a redirect looks odd, but it is what lets one deployed resolver answer for an unbounded namespace, with the data staying live rather than frozen at registration time. Worth noting the gateway is trusted today: the callback passes its answer straight through. Signing responses so the resolver can check them on-chain is the obvious hardening.

Under the hood — ENS

A hex digest will not fit in a name

Wildcard resolution encodes the name in DNS wire format, where a single label is capped at 63 bytes. A SHA-256 digest in hex is 64 characters — 66 with 0x. Clients reject it before a single request leaves the machine.

hex d3ab…1274.binarystamp.eth 64 chars — rejected base36 59x6n7u66bsd…rpkdw.binarystamp.eth 50 chars — resolves

Same 256 bits

Base36 is denser than hex, so the whole digest survives — nothing is truncated.

Padded to fixed width

Without it a digest with leading zero bytes would encode short, and names would stop mapping one-to-one onto hashes.

Two names per stamp

By digest — derivable from the file alone — and by stamp number, which is shorter to share.

The reverse direction is used too: an owner's address is resolved back to their primary ENS name for display. That name is only shown if resolving it forward returns to the same address — otherwise anyone could claim to be anyone.

Under the hood — The Graph

Contracts store state; history lives in events

Asking a contract “who owns this hash” is cheap. Asking “who has ever owned it, and when did each change happen” is not — that history exists only as logs. A subgraph indexes those logs into something queryable.

contract emits StampCreated · StampTransferred │ subgraph indexes them into Stamp every stamp, with its metadata Transfer each change of ownership FileHashLookup digest → current owner, in one hop OwnerStats what an address holds

Instant verification

A lookup is one indexed query rather than a scan across chain history.

Full provenance chain

Every transfer is retained, so the whole ownership trail can be replayed.

It answers ENS too

The CCIP gateway and the provenance agent both read from the same index.

Under the hood — Sui and Walrus

Ownership as an object, metadata as a blob

Sui models assets as objects rather than ledger entries, which suits a stamp precisely: the record is a thing you hold, and transferring it moves the object itself rather than editing a field that claims who owns it.

Move contract
A stamp is an object owned by your address. A shared registry anchors the package; events carry the history.
Transfer means transfer
The object is passed by value to its new owner — not marked as theirs while staying in your account.
Walrus blobs
Optional metadata — description, context, a result digest — stored as a decentralized blob rather than as expensive chain data.
Bound by digest
The stamp records the blob's hash, so altered metadata no longer matches what was stamped.

Same digest, two chains, independently verifiable. Stamp on Base, on Sui, or on both — a claim that does not depend on any single network surviving.

Future improvements

Where it goes from here

Mainnet, and cheaper stamps

Move beyond testnets, and batch many digests into one transaction under a Merkle root so a stamp costs a fraction of a cent.

From assertions to proofs

Attach attestations to computation stamps — signed enclave receipts, or zero-knowledge proofs — so a result is verifiable without re-running it.

An agent-facing API

An SDK and MCP server so agents stamp and query results as a normal step, with sponsored gas so they need no wallet funding.

Richer metadata schemas

Typed records for licences, authorship and derivation, so a stamp can express “derived from” and not merely “exists”.

Stronger identity

Bind stamps to verified identities or organisations, so a signature carries a reputation rather than only an address.

Fuzzy matching

Perceptual hashes alongside exact digests, to recognise a re-encoded image or a lightly edited document.

In one line

Drop a file. Keep the proof.

A permanent, independently checkable record that a particular file existed at a particular moment and belonged to a particular key — established without disclosing anything, and verifiable by anyone, long after we are gone.
